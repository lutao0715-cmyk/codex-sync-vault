## 30 秒快速开始

> 只做三件事，就能拿到一份按国标排版的公文。

**第 1 步 · 说需求**（一句话即可）

```
帮我写一份人力资源部 2025 年度工作总结，3000 字左右
```

**第 2 步 · 等生成**（Skill 自动跑完三阶段）

```
识别类型 → 套模板 → 按 GB/T 9704 排版 → 输出 Word
```

**第 3 步 · 要 PDF 就再补一句**（可选）

```
转成 PDF
```

会自动调用你本机的 Word 或 LibreOffice 转换，并**实测校验页数与字体嵌入状态**
（这两项决定"发到别人电脑上会不会跑版"）。见 [输出侧：格式转换](#输出侧格式转换)。

**第 4 步 · 验收**（推荐跑一次评分，90 分 A 档可直接提交）

```
python scripts/quality_score.py 你的文档.docx
```

⚠️ **三种素材要先转成文字**（本 Skill 不能直接读）：**图片** / **扫描 PDF** / **语音录音**。
转好文字再发给我，处理方法见 [素材转换与降级指南](#素材转换与降级指南)。

## 概述

本技能覆盖国央企和党政机关体系的正式公文写作全流程：格式规范（GB/T 9704-2012 及企业标准扩展）、**38 种模板框架**（8 种工作模板 + 7 种行政公文 + 10 种专题模板 + 信函式文件 + 应急预案/会议议程/慰问信/专项总结/联合行文/转发性公文/请示批复联动/制度办法标准/通报/公示/感谢信贺信/会议方案）、**红头文件一体化生成**（版头要素确认、编排与置入）、公文专用措辞规范及安全保密要求；成稿后可用 `scripts/quality_score.py` 做五维 100 分质量评分（合规/完整/规范/准确/文风），用 `scripts/format_check.py` 做国标排版校验（含版头要素校验），用 `scripts/policy_cite.py` 做政策引用溯源校验，用 `scripts/pdf_export.py` 把 Word 直出为 PDF 并实测校验字体嵌入。核心参考资料存放在 `references/` 目录，按需加载。

## 完整上手示例（Quick Start）

**用户请求**：「帮我写一份人力资源部年度工作总结」

**执行流程**：
1. 识别关键词"年度"+"总结" → 年度工作总结
2. 加载 `references/report-templates.md` 第一节获取框架
3. 加载 `references/vocabulary-guide.md` 获取用语规范
4. 按四段式结构生成内容（主要成效→亮点→问题→计划）
5. 加载 `references/gb-t9704-format.md` → 使用 `docx` skill 按国标排版
6. 审校检查后输出 Word 文档，附安全提示

## 安全红线（所有任务的第一优先级）

执行任何写作任务前，必须完成以下检查：

1. **识别涉密信号**：若用户输入中包含以下任一信号，立即提醒而非继续处理：
   - 密级标注（绝密/机密/秘密）
   - 文件编号含"密"字样
   - 军工项目代号、武器型号
   - 未公开的组织架构或编制信息
   - 具体的技术参数或经费数据
2. **区分占位符**：
   - 敏感信息（涉密内容）→ 拒绝处理，要求用户脱敏后重新提交
   - 可选信息（用户未提供但可自行补充的数据、人名、部门名）→ 用 `XX` 占位
   - 公开信息（用户明确提供的内容）→ 直接使用
3. **本地处理原则**：优先使用 `docx` skill 在本地生成文件，不使用需要上传的外部服务
4. **交付时的保密提醒**：每份文档输出后必须附带安全提示模板

## 工作流程（三阶段）

### 阶段一：准备 — 理解任务并加载资源

```
步骤 1：解析用户请求
├── 包含具体报告类型关键字 → 直接识别，跳至步骤2
├── 表述模糊（如"写个报告"）→ 从模板列表中提供 2-3 个最可能的选项供用户确认
├── 附有素材文件 → 先读取素材（支持 .docx / .txt / .md / 通用PDF），
│   如素材为图片/扫描PDF/语音转写，告知用户需文字化后处理
├── 要求按某份已有文件风格仿写 → 启动「风格仿写流程」（见下方步骤1c）
├── 要求导出 PDF → 走「输出侧：格式转换」的 PDF 直出流程（scripts/pdf_export.py）
├── 要求核查政策引用 / 生成溯源表 → 走「政策引用与溯源」（scripts/policy_cite.py）
└── 用户选择"逐步引导"模式 → 切换为分步交互模式（见下方）

步骤 1b：分步交互模式（用户说"引导我写"或"一步一步来"时启用）
├── 步骤引导：逐项提示用户输入关键信息，每次只问一个问题
├── 要素填空：列出核心要素表格（报告类型/时间范围/关键数据/特殊要求），用户填写后套模板生成
└── 默认模式：快速生成（用户一句话 → AI 直接输出完整文档）

步骤 1c：风格仿写流程（用户提供往年材料，要求新稿风格一致时启用）
1. **提取风格指纹**：读取用户上传的往年材料，分析并记录：
   - 标题风格：常用句式、对仗方式、字数偏好
   - 段落节奏：长短句比例、每段行数、是否习惯「总—分」结构
   - 用词偏好：高频动词（推进/加强/着力）、程度副词档位（显著/较大幅度/一定）
   - 数字呈现方式：先用百分比还是绝对数、是否列表化
   - 语气基调：直接了当/中庸稳重/积极进取
2. **确认风格要点**：向用户简要汇报提取的风格特征（3-5 条），请用户确认
3. **套用风格生成**：基于模板框架 + 用户提供的风格指纹，生成新稿
4. **风格一致性自检**：
   - 新稿与往年材料的小标题对仗方式是否一致
   - 用词偏好是否延续（如往年爱用「持续深化」，新稿也应有对应）
   - 整体语气是否与前作统一

步骤 1d：风格仿写用户提示模板
```
我已分析您往年材料的写作风格，核心特征如下：
1. 标题风格：[X字对仗，如"强化XX、深化XX"]
2. 用词偏好：[高频词，如"着力""狠抓""落地"]
3. 数据呈现：[百分比为主/绝对数为主/表格化]
4. 语气基调：[务实/进取/稳重]

请确认以上风格描述是否准确，或指出需要调整的地方。
确认后我按此风格生成新稿。
```

步骤 2：加载参考资料（按需组合，避免全量预载）
├── 涉及报告框架 → 加载 references/report-templates.md（定位到对应章节）
├── 涉及国标排版 → 加载 references/gb-t9704-format.md（生成 Word 时必加载）
├── 涉及措辞润色 → 加载 references/vocabulary-guide.md + expression-library.md（语境表述库）
├── 涉及范文参考 → 加载 references/case-examples.md（按条线定位：HR/财务/党建/安全/科研）
├── 涉及政策引用 → 加载 references/policy-database.md（速查）+ references/policy-citation-guide.md（格式与溯源规范）
└── 涉及制度/办法/标准类文书 → 加载 references/report-templates.md 第三十五节
```

### 阶段二：生成 — 按框架填充内容

```
步骤 3：信息补全
├── 模板框架中需要但用户未提供的关键信息 → 用 XX 占位，在安全提示中提醒
├── 用户未明确的数据（如"增长率XX%"）→ 用 XX% 占位
└── 用户提供的所有公开内容 → 直接使用，不擅自改写事实

步骤 4：输出格式
首选 Word (.docx)，严格遵循 GB/T 9704-2012 国标排版参数：
- 页面：A4，上3.7cm / 下3.5cm / 左2.8cm / 右2.6cm
- 标题：二号方正小标宋简体，居中，行距固定值30磅
- 正文：三号仿宋_GB2312，行距固定值28磅，首行缩进2字符
- 一级标题（一、）：黑体三号，居中独立成段
- 二级标题（（一））：楷体_GB2312三号，首行缩进2字符
- 三级标题（1.）：仿宋_GB2312加粗三号
- 数字统一使用 Times New Roman
- 若系统缺少指定字体 → 使用 docx skill 设置字体名后提醒用户自行安装字体
- 标题字号分级：党组/党委文件用 20 磅，单位/部门文件用小二号（18 磅），其余用二号（22 磅），默认按用户单位层级推断

备选格式：
- 用户要求 HTML 预览/Markdown → 对应格式输出，告知正式提交仍需 Word
- 用户要求 PDF → 走下方「输出侧：格式转换」的 PDF 直出流程，不自行降级出稿
- 用户要求空模板 → 按 GB/T 9704 参数生成一份空白文档（用户可在 Word 中另存为 .dotx 复用）

格式自检（可选）：
- 生成后可用 `python scripts/format_check.py <docx文件>` 自动检查页边距/字体/行距/层级序号/年份括号
- 脚本跨平台兼容（Windows/macOS/Linux），支持 `--json`（程序化调用）与 `--quiet`（仅问题项）参数；路径支持引号包裹与 `~` 展开
```

### 阶段三：交付 — 审校与安全提示


## 语气与语言规范（合并版）

### 总体原则
客观、严谨、准确、简洁。以事实和数据为基础，避免主观情绪和夸张修辞。立场正确、政治站位高。

### 必须做到
- 正式规范，不含口语化表达
- 小标题对仗工整（四字或六字动宾短语）
- 政策术语严格准确（不可自行修改/发明政治表述）
- 问题表述用"有待加强""存在不足""尚需提升""仍有差距"
- 数据有来源、逻辑有支撑

### 禁止使用（集中列出一处）
- ❌ 口语词：搞、弄、做、干、整 → 替换为：开展、办理、实施、推进、处理
- ❌ 绝对化用语：完全、绝对、100% → 替换为：基本、较为、显著
- ❌ 夸张修辞：史无前例、前所未有、极大突破
- ❌ 情绪化表达：非常、特别、极其
- ❌ 模糊表述：大概、可能、好像、差不多

### 常用句式速查
| 场景 | 句式 |
|------|------|
| 开头 | "为深入贯彻落实……，根据……要求，现就……如下：" |
| 过渡 | "现将有关情况报告如下：" |
| 总结 | "总的来看，……" / "通过……，取得了以下成效：" |
| 部署 | "要……，要……，要……" / "着力抓好……" / "持续深化……" |
| 问题 | "主要表现在：一是……二是……三是……" |

## 边界条件与异常处理

| 场景 | 处理方式 |
|------|----------|
| 用户提供图片/扫描PDF/语音 | 告知无法直接解析，请用户提供文字内容 |
| 请求类型不在模板列表中 | 如为特定行政公文则按对应模板生成；确实未覆盖的按最接近类型变通处理 |

| 生成失败/输出异常 | 重试一次；重试仍失败则输出 Markdown 降级版本并说明原因 |
| 用户输入超出技能边界（如英文、法律文书） | 明确告知能力边界，给出替代建议或引导使用其他工具 |

## 政策引用与溯源

> 公文与一般文章最大的区别：**每一个政策依据都要能被审核人查证**。
> 本 Skill **不联网**，所以这里的"溯源"指的是——**把引用写规范、把要素补齐、把待核对项列清楚**，
> 事实核验必须由用户比对官方原文。

**完整规范见 [`references/policy-citation-guide.md`](references/policy-citation-guide.md)**，要点：

| 事项 | 要求 |
|------|------|
| **引用式样** | `根据《文件全称》（发文字号，发布日期）精神……` |
| **发文字号** | 用**六角括号** `〔〕`，不用 `[]` `（）` `【】`——这是公文审核高频扣分点 |
| **四种标识** | 〔〕式文号 / 令式文号（主席令第X号）/ 标准编号（GB/T 9704-2012）/ 法律法规（标注版本年份） |
| **首引与后续** | 首次用全称加书名号附文号；后续可用「该文件」指代；**同一文件前后写法必须一致** |
| **来源优先级** | ① 中国政府网/国务院政策文件库 → ② 部委官网（.gov.cn）→ ③ 省级政府官网/地方政策法规库 → ④ 人民日报/新华社 |
| **时效性核验** | 发布日期与生效日期 → 是否被修订 → 是否已废止 → 时段性政策是否仍在有效期 |
| 🔴 **红线** | **绝不编造**文件名称、发文字号、条款内容；**严禁将外省政策作为本省政策依据** |

**查不到原文时的三种占位写法**（按优先级）：

| 写法 | 适用 | 示例 |
|------|------|------|
| 缓冲表述 | 方向明确、具体文件未定 | 「根据国家和本市关于人才引进的有关要求……」 |
| 待补标注 | 文件已定、文号/日期未查到 | 「根据《××管理办法》（**〔待补：发文字号、发布日期〕**）……」 |
| 待核标注 | 记得有这份文件、表述拿不准 | 「根据《×××》（**待核：文件全称与现行版本**）的部署……」 |

**跑一次自动校验 + 生成溯源表**：

```bash
python scripts/policy_cite.py 报告.docx --save 报告-政策引用溯源表.md
```

脚本检出 7 类问题：缺发文字号 / 缺日期 / 括号不规范 / 带待补占位 /
书名号不成对 / 同一文件两种写法 / 文号年份异常。输出的 Markdown 溯源表**可直接附在稿子后面交付**。

> ⚠️ **脚本不做事实核验**——文件是否真实存在、是否已修订或废止、条款内容是否对应，
> 必须由用户比对官方原文。脚本的价值在于把"凭着感觉翻"变成"照着清单查"。

## 错误处理与降级机制

> 目标：任何异常场景下，Skill 都应给出可用的输出或明确反馈，而不是静默失败或产生乱码。
> 设计原则：**检测 → 分类 → 重试上限 2 次 → 降级输出 → 明确告知**。不允许静默失败。
>
> **完整规则（E1-E13 逐条含"为什么会这样"）见 `references/troubleshooting.md` 第二部分。**
> 下面只给速查表——**遇到问题先查这张表，再翻详细规则**。

### 遇到问题查这里（13 条速查）

| 你会看到 | 编号 | 一句话处置 |
|---------|:---:|-----------|
| 打开文档字体不对 | **E1** | 装字体即可；不装也能用，只是观感差 |

| 提示"这个对话太长了" | **E3** | 开新对话带上前半部分和剩余大纲，接着写 |
| 生成失败 / 输出乱码 | **E4** | 会给你 Markdown 版，内容是全的 |
| 你让写英文公文 / 合同，我没动笔 | **E5** | 超出范围，会告诉你该用什么工具 |
| 一次要好几份，我一份份出 | **E6** | 同时做会互相干扰，逐份更干净 |
| 只说"写个报告"，我反问你 | **E7** | 文种选错要整体返工，问一句更省事 |
| 我拒绝了请求，只说"请脱敏" | **E8** | 涉密信息是硬规则，脱敏后再发 |
| 提示"本次未执行自动评分" | **E9** | 文档照常交付，可照清单自己核 |
| 提示"单位名称含敏感词，请确认" | **E10** | 回一句"可以公开"即可继续 |
| 文中出现《XXXXX》（待核实） | **E11** | 按清单补原件信息，我不替你编 |
| 只给了框架和待补清单 | **E12** | 占位太多；补内容或说"先出草稿" |
| 提示"PDF 好了但字体没嵌入" | **E13** | 正式发文勾选 PDF/A；内部传阅可忽略 |

### 三条通用边界（硬规则）

1. **不允许静默失败**——任何异常都要明确告知，不能悄悄跳过
2. **不谎报完成**——只有真的产出文件并校验通过才算完成
3. **讲人话不说机制名**——对用户说"你可以这样做"，不说"降级""兜底""回退路径"

## 交付前成果检核（E-有效性保障）

每份文档交付前必须通过下列检查，任何一项未通过需修正后重交：

**硬性检查（必须 100% 通过）**

1. ✅ 报告类型与用户请求一致
2. ✅ 关键占位符全部已用 `XX` 标记，未遗漏
3. ✅ 涉密信号扫描通过（无密级标注、无项目代号）
4. ✅ 政治术语准确（对照 vocabulary-guide.md）
5. ✅ 层级标题序号格式正确（一、→（一）→ 1.→（1））
6. ✅ 字体/行距/页边距符合 GB/T 9704-2012
7. ✅ 安全提示已附在交付说明末尾
8. ✅ 政策引用要素完整（引用 ≥3 处时：`policy_cite.py` 显示「必须处理 0 项」）

**软性检查（建议通过）**

9. ⭐ 小标题对仗工整（四字/六字动宾短语）
10. ⭐ 数据前后一致，单位统一
11. ⭐ 篇章过渡自然（无突兀转折）
12. ⭐ AI 痕迹扫描通过率 ≥ 95%（对照 ai-traces.md 12 类）
13. ⭐ 搭配不当 5 类已过（对照 polishing-guide.md §1.2.1）
14. ⭐ 要求 PDF 时：字体嵌入状态已实测并告知用户

如硬性检查未通过，**必须修正后重交**；如软性检查未通过，需在交付说明中标注「存在 X 项建议优化项，用户可酌情调整」。

## 交付时附格式校验报告（L-3）

> **为什么要附**：用户拿到文档后，最常被问的两句话是"这个格式对不对""能不能直接交"。
> 与其让用户自己跑脚本、自己判断，不如**把校验结果随文档一起给出去**——
> 一份逐项打勾的清单，用户扫一眼就知道哪里还没过，需要处理的项一眼可见。

### 触发条件

| 情况 | 是否附报告 |
|------|:---:|
| 生成了 .docx 文件 | **必附** |
| 只输出了 Markdown（降级模式） | 不附（无版式可校验） |
| 用户明确说"不用检查/赶时间" | 不附，但要在交付说明里注明未校验 |
| 用户要求"核一下格式" | 附，且把详细报告一并给出 |

### 报告内容（固定三块）

交付说明中按下面结构给出，**不要整段贴脚本原始输出**：

```
一、格式校验（GB/T 9704-2012）

  ✅ 页边距      上3.7 / 下3.5 / 左2.8 / 右2.6 cm
  ✅ 标题字体    方正小标宋简体
  ✅ 正文字体    仿宋_GB2312（三号）
  ✅ 一级标题    黑体三号
  ✅ 二级标题    楷体_GB2312 三号
  ✅ 行距        标题 30 磅 / 正文 28 磅（固定值）
  ✅ 首行缩进    2 字符
  ✅ 页码        4 号宋体（单页码居右、双页码居左）
  ⚠️ 数字字体   未显式设置 Times New Roman（建议设置）
  ❌ 标题缩进    第 3 段缩进值 200，应为 2 字符

  结论：9 项通过 / 1 项提示 / 1 项待修
  → 待修项已定位到具体段落，可按上面说明直接改

二、质量评分（- 可选，脚本可用时附）

  总分 92 / 100（A 档，可直接提交）
  ├ 合规度 30/30   ├ 完整度 24/25   ├ 规范度 20/20
  ├ 准确度 13/15   └ 文风 5/10

三、需要你处理的事项（- 没有则写"无"）

  1. 第 3 段首行缩进需调整为 2 字符
  2. 建议给数字设置 Times New Roman 字体
  3. 文中 3 处「XX」占位符待补充（清单见下）
```

### 生成方式

```bash
# 1) 格式校验（必须）
python scripts/format_check.py 你的文档.docx

# 2) 质量评分（可选，Python ≥ 3.7 时可用）
python scripts/quality_score.py 你的文档.docx

# 3) 政策引用核查（文中引用政策时）
python scripts/policy_cite.py 你的文档.docx

# 4) 一次性跑全部（推荐，直接出报告）
python scripts/preflight_check.py          # 环境自检
```

如需程序化取用（比如生成 JSON 再排版），加 `--json`：
```bash
python scripts/format_check.py 你的文档.docx --json
```

### 三条硬规则

1. **不谎报通过**：脚本报 `❌` 的项目必须照实写进报告，**不允许"看起来不影响就不提"**
2. **不贴原始输出**：给用户的报告用上面的三段结构，把脚本输出里的路径、退出码、
   机制名（如 "sectPr/pgMar"）翻译成人话
3. **待修项要给位置**：只写"缩进异常"没用，要写"**第 3 段**缩进值 200，应为 2 字符"

### 与 E9 的关系

评分脚本跑不起来时（见 E9），**格式校验报告仍要照常给**——`format_check.py` 与
`quality_score.py` 是独立的，前者失败不影响后者，反之亦然。报告里注明哪一块没跑成即可。

## 出错了怎么救（L-6 故障自动恢复三式）

> 用户遇到报错时最需要的不是错误原因，而是**"我现在该干什么"**。
> 下面三式覆盖绝大多数可恢复故障，**优先自己执行，不要先问用户**。

### 第一式：换路径（文件找不到 / 打不开）

**症状**：报错说文件不存在、路径无效、无法打开。

**处置顺序**（自己试，别先问用户）：

```
1. 换算绝对路径重试（相对路径在不同工作目录下会失效）
2. 去掉路径两端引号重试（拖拽文件常带引号）
3. 若路径含空格或中文，用双引号包住重试
4. 都失败 → 才问用户："方便的话把文件重新拖一次给我，或者告诉我完整路径"
```

**为什么先自己试**：这几类问题占了"文件打不开"的绝大多数，且**修改方式没有歧义**，
试错成本远低于来回问一次。

### 第二式：无缝续写（生成中断 / 上下文超限）

**症状**：写到一半停了、提示上下文过长、输出被截断。

**处置顺序**：

```
1. 立刻记录断点：已完成的章节范围 + 下一个该写的章节
2. 主动向用户报断点："已写到第 4 章，从第 5 章接着写"
3. 让用户开新对话，把「已完成部分 + 剩余大纲 + 本文种的格式要求」一并带过去
4. 新对话里从断点续写，不重写已完成部分
```

**关键**：断点信息要**明确到章节号**。"写到一半"这种说法用户没法接。

### 第三式：只重做受影响的那一步（部分失败）

**症状**：多步骤任务里某一步失败（如内容已生成但排版失败、评分失败但文档正常）。

**处置顺序**：

```
1. 先判断：失败的是「必要步骤」还是「附加步骤」
   - 必要步骤（生成内容 / 输出文档）→ 必须重做
   - 附加步骤（评分 / 格式校验 / PDF 转换）→ 可跳过并告知
2. 只重跑失败的那一步，不从头再来
3. 附加步骤失败时，在交付说明里注明"该项未完成"，其余照常交付
```

**为什么不一键重来**：重跑全部步骤会把已完成的内容重新生成一遍，
**既浪费时间，还可能让已经确认好的内容发生变动**（用户可能已经改过）。

### 三式速查

| 症状 | 用哪一式 | 先自己试还是先问用户 |
|------|:---:|:---:|
| 文件找不到 / 打不开 | 第一式 · 换路径 | **先自己试**（4 步） |
| 生成中断 / 上下文超限 | 第二式 · 无缝续写 | 主动报断点，再请用户配合 |
| 评分 / 校验 / PDF 失败 | 第三式 · 只重做该步 | 附加步骤可直接跳过并告知 |

## 脚本参数速查表（Y-2：要改哪里、怎么改）

> **为什么单列一节**：脚本报告有时会说"某段偏离标准"，但**没告诉你参数在哪改**。
> 下面把所有可调项一次列清——**先看"你想干什么"，再到对应行找命令**。

### 零、最常用的四条命令

```bash
# 生成文档后，一次跑完格式校验 + 质量评分
python scripts/format_check.py 你的文档.docx
python scripts/quality_score.py 你的文档.docx

# 文件打不开时，先试这个（探测环境与可用通道）
python scripts/preflight_check.py

# 要 PDF 时，先探测有没有转换引擎
python scripts/pdf_export.py --check
```

### 一、format_check.py（格式校验 / 排版层）

| 你想干什么 | 命令 | 说明 |
|-----------|------|------|
| 检查一份文档 | `python scripts/format_check.py 文档.docx` | 默认输出通过项/提示项/问题项 |
| 只看问题，不看通过项 | `python scripts/format_check.py 文档.docx --quiet` | 排障时用，输出最短 |
| 给程序读（生成 JSON） | `python scripts/format_check.py 文档.docx --json` | 交给别的工具处理 |
| 看脚本版本与运行环境 | `python scripts/format_check.py --version` | 排障先看这个 |

**参数就这几个**，没有更复杂的选项。报告里说"某段偏离"，对应的是
「行距（正文/标题）」「首行缩进」「页边距」这几类，**改文档本身即可**，
不需要改脚本。

### 二、quality_score.py（质量评分 / 文本层）

| 你想干什么 | 命令 | 说明 |
|-----------|------|------|
| 给文档打分 | `python scripts/quality_score.py 文档.docx` | 五维 100 分制 |
| **告诉脚本这是什么文种** | `--type 年度工作总结` | **最重要的一项**，见下方类型表 |
| 写的是草稿，占位符别扣分 | `--draft` | 跳过占位符检查 |
| 只看问题项 | `--quiet` | 简洁输出 |
| 看全部检查项（含通过） | `--verbose` | 想彻底了解扣分来源时用 |
| 生成 JSON | `--json` | 程序化取用 |

**支持的 13 种类型**（`--type` 的值，照抄即可）：

```
年度工作总结 / 述职报告 / 党建报告 / 调研报告 / 工作方案 / 整改方案
会议纪要 / 通知 / 请示 / 汇报材料 / 转发性公文 / 批复 / 制度标准
```

> **不指定 `--type` 会怎样**：脚本会自己猜（看标题关键词）。
> **猜错的后果是"章节完整性"扣分不对**——比如把「工作方案」猜成「年度工作总结」，
> 就会要求你写"工作亮点""存在问题"这些方案里本来没有的章节。
> **所以文种明确时，建议显式指定。**

### 三、policy_cite.py（政策引用核查）

| 你想干什么 | 命令 | 说明 |
|-----------|------|------|
| 查引用有没有问题 | `python scripts/policy_cite.py 文档.docx` | 检 7 类问题（缺文号/缺日期/括号/待补/书名号/异称/年份） |
| **生成溯源表并保存** | `python scripts/policy_cite.py 文档.docx --save 溯源表.md` | 输出可交付的政策引用清单 |
| 只看问题项 | `--quiet` | |
| 生成 JSON | `--json` | |

### 四、pdf_export.py（PDF 转换）

| 你想干什么 | 命令 | 说明 |
|-----------|------|------|
| **先看有没有转换通道** | `python scripts/pdf_export.py --check` | **转之前先跑这个**，别直接转 |
| 转换（自动选通道） | `python scripts/pdf_export.py 文档.docx` | 默认 `--method auto` |
| 指定用 Word 通道 | `--method word` | 需装 Microsoft Word |
| 指定用 LibreOffice 通道 | `--method libreoffice` | 需装 LibreOffice |
| 指定输出路径 | `--out 输出.pdf` | 默认与源文件同目录同名 |
| 只看结论 | `--quiet` | |

### 五、表格：常见报错 → 改哪个参数

> **这张表是本节的核心**。左边是脚本报的话，右边是你要动的地方。

| 脚本报的话 | 实际含义 | 你要改什么 |
|-----------|---------|-----------|
| `❌ 行距（正文）: N 段偏离 28 磅` | 正文段落行距不是固定值 28 磅 | 文档里把正文段落行距设为**固定值 28 磅** |
| `❌ 行距（标题）: N 段偏离 30 磅` | 标题段落行距不是固定值 30 磅 | 标题段落设为**固定值 30 磅** |
| `❌ 首行缩进: N 段缩进值异常` | 缩进不是 2 字符（约 400-700 twips） | 设为**首行缩进 2 字符** |
| `❌ 页边距 xxx: 当前 X cm, 应为 Y cm` | 页边距不符国标 | 设为 上3.7 / 下3.5 / 左2.8 / 右2.6 cm |
| `❌ 标题字体: xxx, 应为方正小标宋简体` | 标题字体不对 | 标题字体设为**方正小标宋简体** |
| `❌ 页码: 字体非宋体...` | 页码字体/字号/对齐不符国标 | 页码设为 **4 号宋体**，单页码居右、双页码居左 |
| `❌ 年份括号: 发现使用方括号[]` | 年份用了 `[2026]` | 改成六角括号 **〔2026〕** |
| `⚠️ 数字字体: 未设置 Times New Roman` | 建议项，不强制 | 数字设为 Times New Roman（可选） |
| `未识别报告类型` | 猜不出文种，按默认章节判分 | 加 **`--type 你的文种`** |
| `章节缺失: 工作亮点` | 报了你文档里本来就该没有的章节 | 多半是类型猜错，加 **`--type`** 纠正 |
| `未替换占位符 N 处` | 正文里还有 `XX` | 补全内容；**草稿加 `--draft`** |
| `未检测到 Word/WPS/LibreOffice` | 本机没有转换引擎 | **先跑 `--check`**；无引擎走三条降级路径（见 PDF 前置条件节） |
| `源文件正被占用` | 文档还开着 | **先关掉 Word/WPS 里的这个文档**再转 |
| `路径不存在 / 无法打开` | 路径问题 | 用绝对路径 + 去掉引号 + 含空格加双引号（见 L-6 第一式） |

### 六、三个"改文档"与"改参数"的区分

| 报错类型 | 改哪儿 | 例子 |
|---------|-------|------|
| **文档内容/版式问题** | **改文档**，不改命令 | 行距、缩进、字体、括号 → 都是文档的事 |
| **脚本判断口径问题** | **加参数** | `--type`（文种）、`--draft`（草稿）、`--method`（通道） |
| **环境问题** | **改环境** | 没装 Office → 换电脑或手动导出（不能靠参数解决） |

> **一句话**：**加参数只解决"脚本判错了"，不解决"文档写错了"**。
> 看到行距/字体/缩进类报错，直接去改文档；看到章节/类型/占位符类报错，才考虑加参数。
