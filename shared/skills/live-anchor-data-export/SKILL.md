# 直播间主播数据导出（15列完整版，2026-09-14 最新流程）

## 概述

输入两份文件 → 输出主播累计数据 xlsx（15 列）。高频复用任务（涛哥每两三天导一次）。

- **大表明细**：二台跨天*.xlsx / 二台直播间明细*.xlsx —— 直播级明细，每行=某直播间某天（跨天直播会**一个直播间多行**）
- **基准名单**：导出直播活动内容列表*.csv/.xlsx —— 活动排期，决定"统计哪些直播间"

> ⚠️ **第一原则：拿到任何文件先扫表头/结构，不要吃老本。** 同名文件每次上传结构都可能变（128列表格0 / 120列Sheet2 / 22版sheet1 / 单sheet多sheet 都出现过），列号不能硬编码。直接跑一键脚本可自动处理。

## 🚀 一键导出（推荐）

`~/.workbuddy/skills/live-anchor-data-export/scripts/export_14col.py` 已内置全部逻辑：

```bash
python3 ~/.workbuddy/skills/live-anchor-data-export/scripts/export_14col.py \
  "<大表明细.xlsx>" "<基准名单.csv|xlsx>" \
  -o "/Users/lutao/Downloads/主播累计数据_MMdd.xlsx"
```

脚本自动完成：
1. 自动选数据行最多的 sheet；`reset_dimensions()` 处理维度 1x1
2. **按表头关键词定位列**（日期/创作者/昵称/直播ID/播放总时长/曝光次数/点击次数/播放次数/播放用户数/互动用户数/累计粉丝量/人均观看时长/关注成功/拉新）
3. 直播间 ID **跨天多行先累加**
4. 基准若有多个 ID 列 → **实测命中率选最高者**（A列"直播id"常命中0，B列"直播间ID"才对）
5. 数值去千分位文本（"1,234"）
6. 按主播聚合 → 粉丝净增 **max-min**、开播天数=命中明细行日期去重（一天多场算1天）→ 写 15 列 xlsx
7. 打印全量明细 + 合计 + 异常提醒（曝光0但有播放用户、点击>曝光的脏日）

## 15 列输出定义

| # | 列名 | 口径 |
|---|------|------|
| 1 | 主播昵称 | 取自大表（明细带出的创作者昵称） |
| 2 | 主播ID | 大表"创作者ID" |
| 3 | 开播场次 | 基准直播间去重计数（按该直播间首条明细归属主播） |
| 4 | 开播天数 | **按「直播开始时间」的真实开播日去重**（2026-09-20 修正：跨天直播的大表「日期」列记次日，会把两场压成一天；如东北乒乓侠 16 场被压成 11 天。无开始时间列时回退明细日期）。一天多场算 1 天 |
| 5 | 累计播放总时长(小时) | Σ 播放总时长列（单位已是小时） |
| 6 | 累计直播曝光次数 | Σ 曝光 |
| 7 | 累计直播播放用户数 | Σ 播放用户数 |
| 8 | 累计直播互动用户数 | ⚠️ 是**互动用户数**不是互动次数（120列版在36列/128列版在44列，别取到互动次数列） |
| 9 | 累计直播间关注成功用户数 | Σ 关注成功 |
| 10 | 累计app手机拉新首播用户数 | Σ 拉新 |
| 11 | 累计粉丝量净增(活动期max-min) | 该主播名下**全部 fans 记录 max − min**（2026-09-07 涛哥确认口径，见下） |
| 12 | 人均观看时长(分钟) | Σ(人均观看时长列 × 该场播放用户数) ÷ Σ播放用户数（按播放用户数加权，非简单平均） |
| 13 | 互动率(%) | 互动用户数 ÷ 播放用户数 × 100 |
| 14 | CTR(%) | 点击次数 ÷ 曝光次数 × 100（点击>曝光的异常日会失真，低量主播尤其） |
| 15 | 次均播放时长(分钟) | 播放总时长×60 ÷ 播放次数（注意分子分母别写反） |

⚠️ 原表常见脏数据：小流量日"点击>曝光" → 聚合 CTR>100%（如探险家马羽 678%）甚至 664%，分析此类主播时以互动率/推荐转化率/次均时长为准，不要只看 CTR。

## 多维转化分析与主播分层（2026-09-14 新增）

脚本：`scripts/analyze_multidim.py <大表> [名单.xlsx] -o 输出.xlsx`
（默认名单取 `~/Downloads/报名成功主播_累计数据_0914v2.xlsx` 的「名单ID」列）

**关键认知：名单里的「咪咕账号ID」= 大表的「创作者ID」，不是直播间ID。**
按直播间ID匹配会 100% 落空；按创作者ID归集才对（场次另用直播间ID去重）。

维度与口径（全部按量加权，不用简单平均）：
| 维度 | 公式 | 权重 |
|---|---|---|
| 曝光转化率 CTR | Σ点击次数 ÷ Σ曝光次数 | 20% |
| 次均曝光带来时长(秒) | Σ播放总时长(h)×3600 ÷ Σ曝光次数 | 25% |
| 人均观看时长(分) | Σ(人均观看时长×播放用户数) ÷ Σ播放用户数 | 20% |
| 互动率 | Σ互动用户数 ÷ Σ播放用户数 | 15% |
| 千次曝光涨粉 | 粉丝净增 ÷ 曝光 × 1000 | 10% |
| 开播稳定度 | 开播天数 | 10% |
综合分 = 池内百分位 × 权重 × 100；按 1/3 分位切 A 潜力 / B 平平 / C 待突破。

**必做数据清洗（否则结论全错）**：
1. 剔除「点击次数 > 曝光次数」的行（物理不可能；实测有 10003% / 221% CTR 的脏行）；
2. 标记「点击≥曝光且曝光≥500」的高 CTR 行占比 → 超 10% 的主播其 CTR 要打折看（如快乐钓鱼柱子 12.2%）；
3. 可靠性门槛：累计曝光 < 2 万 或 有效场次 < 5 → 归入「样本不足」不参与排名（如熹熹健身舞/玉子很哇塞/不一样的三哥，率值虽高但流量基数太小）；
4. 开播天数 < 7 天不评估。

**易误读案例**（写结论时必须点出）：
- 石祈钓鱼：CTR 11.4% 偏高但秒/曝光仅 6.2 → 标题党式点击，进来就走；
- 啵啵天天酱：曝光 173 万（第 3 大）但 CTR 3.1% 全场最低 → 有量无质；
- 北环大黑：曝光 499 万断层第一、CTR 13.4%、千次涨粉 1.9 全场最高，但与同批主播量级差距过大，结论前先核实是否有平台灌量。

## 曝光侧抗噪分层（2026-09-14 v3，用于「重点主播」类复盘）

脚本：`scripts/analyze_exposure_tier.py`（顶部三个常量改路径即可：A=曝光侧表、B=直播侧累计表、OUT=输出）

**输入特征**：曝光侧表（如「重点主播的开播&转化数据」）每张 sheet 是 **24 个数据块堆叠**（每天一块，块间空行、每块自带表头），
且表头 **4 种变体**（`曝光次数(数量)` vs `曝光次数`、`播放用户数(数量去重)` vs `播放用户数`、
`点击视频总播放时长` vs `点击视频总播放时长(分)` vs `曝光占比`、曝光节目次数位置互换）。
→ 必须逐块解析并按关键词模糊匹配列号（去掉括号空格后 startswith）；**不能按首行表头一把梭**。
缺「点击视频总播放时长」的块用「曝光人均播放时长(分)」× 曝光用户数 反推（口径等价）。

**三个必须做的清洗（否则结论会被推翻）**：
1. **计数列失真**：低流量行常出现「点击次数 > 曝光次数」（实测曝光 27 次/点击 454 次），
   `点击次数` 列不可信 → 全程改用**去重用户级口径**（曝光用户数/点击用户数/播放用户数），各块内部自洽。
2. **噪音日**：单日曝光用户 <200 的天会算出「秒/曝光 2577」这类荒诞值 → 不计入有效曝光日与日中位数。
3. **异常曝光日**：「异常曝光case（标红）」是**直播间曝光口径**，与推荐曝光不是同一分母，**不能相除**；
   按「日期×主播」整日剔除（曝光/点击/时长全不计）。

**指标口径**：
- CTR(曝光用户) = Σ点击用户 ÷ Σ曝光用户
- 秒/曝光 = Σ观看时长(分)×60 ÷ Σ曝光用户
- 观看分钟/播放用户 = Σ观看时长 ÷ Σ播放用户（留人深度）
- 推荐转化率：按曝光用户加权
- 日均曝光用户 = 净曝光用户 ÷ 有效曝光日

**⚠️ 铁律：输出必须覆盖名单全量，一个人都不能丢（2026-09-14 涛哥反馈「怎么只剩17个人了」）**
第一版只把「过门槛的参评池」写进主表，结果 33 人名单里：
- 8 人被归「数据存疑」、5 人被归「样本不足」、**3 人（曝光侧一条记录都没有）被脚本直接 continue 丢掉**，主表只剩 17 人，
  涛哥一眼就问「还有一半的人呢」。**分档不是筛人，所有档位都要出现在同一张主表里。**
- 正确做法：`all = list(recs)` 全员，给每个未定级的人也补 `分层` 字段
  （`S 样本不足` / `⚠️ 数据存疑` / `N 无推荐曝光`），主表 = 全员按档位排序；
  另设「档位汇总」页（档位 / 人数 / 名单 / 处置建议 + 合计=名单全量）放在第一个 sheet，打开即见全貌。
- 分层档位顺序：A 加推主力 → T 质量达标·待给曝光 → B 观察优化 → C 暂缓投入 → P 样本偏薄
  → S 样本不足 → ⚠️ 数据存疑 → N 无推荐曝光。

**闸门与分层**：
- 数据存疑（不参评）：异常日占比 >40% 或 单日曝光集中度 >70%
- 定级门槛：有效曝光日≥8 且 净曝光用户≥5万 且 直播场次≥5；样本底线 5天/3万/3场
- 综合分 = 规模20% + 效率25% + 深度35% + 沉淀20%（池内百分位）
- A 加推主力 = 过门槛 + 日均曝光≥1万 + 效率≥55且深度≥55；T 质量达标·待给曝光 = 质优但未过门槛；
  C 暂缓投入 = 效率与深度双低(<45)；其余 B 观察优化

**教训（重要）**：上一版直接用「Σ播放时长÷Σ曝光」的累加比率，把**单日爆量**当成能力，
结果把北环大黑、快乐钓鱼柱子、大伟路亚这些数据被污染/效率其实很差的判成了「强潜力」。
用日中位数 + 异常日剔除 + 噪音日门槛后，A 档换成了 晴晴-啦啦队长 / 啵啵天天酱 / 67拉拉队 / 哇可爱的贤贤 / 时不时。
**结论里必须点出「上版判为潜力、本版被降级」的原因**，否则涛哥会再质疑一次。

输出 Excel 含 7 页：分层结论 / 全量指标 / 数据存疑剔除 / 样本不足 / 曝光侧日明细（带异常标记）/ 与上版结论对比 / 口径与数据坑。

## 三表联合与口径对齐（2026-09-14 下午，涛哥第三次"感觉不对"后定稿）

脚本：`scripts/join_three_tables.py`（终版评估）/ `scripts/check_ctr_calibers.py`（口径对账）

**核心教训：同一批主播的两版结论打架，根源是曝光口径不同 —— 混用必错。**

| 口径 | 来源 | CTR 水平 | 说明 |
|---|---|---|---|
| 直播间曝光（次数） | 大表「直播曝光次数」 | 全表稳定 4-9%，中位 ~7.5% | 直播间卡片曝光，官方全口径，33人全覆盖 → **打分唯一口径** |
| 推荐场景曝光（用户） | 重点主播的开播&转化数据(1) | 全表稳定 0.5-2% | feed刷到的推荐曝光；**对账发现其「曝光用户」普遍是大表曝光用户和的 150-190%，两者是不同统计维度，非包含关系** |

对账结论（涛哥三次质疑的最终答案）：
1. v3 用推荐侧表打分（CTR 0.9%）、多维版用大表打分（CTR 7-13%），数字差 5-10 倍不是谁算错了，是口径不同；
2. 推荐侧表只覆盖 30/33 人且口径不可比 → 降级为「参考列」，不参与打分；
3. 大表「曝光用户数/播放用户数」是行级去重，跨天求和有重复（点击→播放会出现 >100% 的荒诞值），只用「次数」口径打分；
4. 大表 32 行脏数据（点击>曝光）剔除；CTR>12%（中位 7.5%）或高CTR行占比>10% → 标「⚠️ CTR异常」不参评。

终版打分（大表口径）：转化25%(CTR.55+千次涨粉.45) + 深度30%(人均.6+次均.4) + 互动15% + 规模10%(日均曝光.6+天数.4) + 沉淀20%(涨粉.6+关注.2+拉新.2)。
门槛：参评=曝光≥5万且开播≥5天；A档另需规模分≥45（55 会导致全表无 A）；样本底线=曝光≥1万且开播≥3天。
铁律不变：**33 人全量进主表**（A1/T3/B21/C3/S2/⚠️3=33），档位汇总页放 sheet0。

**注意跨版结论的解释义务**：同一主播在不同口径下分档会变（如东北乒乓侠：推荐口径下数据存疑，大表口径下深度96/互动98 全场第一但 CTR 6.3% 偏低 → B；北环大黑：两个口径下都是异常）。结论里必须说明用的是哪个口径、为什么。

## 用飞书名单过滤（高频变体：只保留「报名成功」主播）

涛哥常见追加要求：「和飞书表的主播id做关联，我只要报名成功的主播明细，不关联的id不要出现在最终表里」。

### 一键脚本

```bash
# 1) 拉飞书名单
lark-cli sheets +csv-get --spreadsheet-token <sheet_token> --sheet-id <sheet_id> \
  --range A2:B40 --include-row-prefix=false --format json > /tmp/roster.json

# 2) 按主播ID关联过滤
python3 ~/.workbuddy/skills/live-anchor-data-export/scripts/join_roster.py \
  "~/Downloads/主播累计数据_0914.xlsx" /tmp/roster.json -o "~/Downloads/报名成功主播_累计数据_0914.xlsx"
```

脚本行为：输出「名单ID / 名单昵称」+ 累计数据表除 ID 外的全部列（ID 只留一列，避免重复）；
另建「未关联备查」sheet 列明两个方向的对不上名单（名单有但数据无 / 数据有但名单无），方便核对。

### ⚠️ 坑：lark-cli user 授权「扫码成功但身份仍 missing」

**完整排障流程见独立 skill `lark-cli-auth-fix`**（含一键修复脚本）。速记：

1. token 其实**已经换到了**（日志 `oauth/token status=200`），只是落盘 rename 被拒；
   CLI 随后重试 → 第二次必然 `device_code is invalid`，**命令行报错具有误导性**。
2. 判断看日志 `~/.lark-cli/logs/auth-YYYY-MM-DD.log`，不要只看 stdout。
3. 绕行：`bash ~/.workbuddy/skills/lark-cli-auth-fix/scripts/fix_token_rename.sh`
   （把遗留的 `<name>.enc.<uuid>.tmp` 改名成 `<name>.enc`），再用 `lark-cli auth status` 验证。
4. 授权二维码：`lark-cli auth qrcode "<verification_url>" -o /tmp/qr.png`（**URL 是位置参数，没有 `--url`**）。
5. device code 只能用一次；`--no-wait --json` 拿到的 code 本轮没用上就作废，要重新发起。
